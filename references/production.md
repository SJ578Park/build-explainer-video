# 대본에서 배포 영상까지

## 내용 설계

프로젝트에 짧은 제작 브리프를 둔다. 청중의 사전지식, 시청 후 설명할 수 있어야 하는 내용, 핵심 주장과 출처, 전체 길이, 언어, 브랜드, 배포 범위, 현장 질문을 기록한다. 해결하지 않은 논쟁은 각 입장과 판단할 근거를 보여준다.

영상 구조는 내용에 맞춘다. 문제정의 워크숍은 `상황 → 불편/증거 → 잘못 설정한 질문 → 재정의 → 검증 방법 → 실습`이 유용하다. 개념 강의는 `구체적 사례 → 원리 → 다른 사례에 적용 → 오해 확인`이 더 적합할 수 있다. 모든 주제를 같은 후킹 문구와 고정 장면 수로 밀어 넣지 않는다.

장면표에는 대본, 화면의 메시지, 효과 ID와 선택 이유, 사용할 근거/자산, 예상 길이, 정지 가능 여부를 담는다. 타이밍이 아직 예상이면 확정값으로 표시하지 않는다.

## 화면과 음성

기본 시작점은 16:9, 1920×1080, 30fps이다. 다른 비율이나 프레임률을 요청하면 그 조건을 따른다. 프로젝트 안에서는 한 가지 프레임 기준을 사용한다. `plan.mjs`의 현재 v1 형식은 정수 fps만 지원한다. 29.97 등 비정수 fps가 필요하면 형식을 먼저 확장하거나 별도 시간 계산을 사용하고 반올림해 속이지 않는다.

1080p에서는 큰 제목 약 64–96px, 본문 약 36–48px에서 검토를 시작한다. 화면 녹화 속 작은 글씨는 관련 부분을 확대한다. 핵심 텍스트는 화면 가장자리에서 약 5% 안쪽에 둔다. 배포용 CC를 켜도 핵심 정보가 가려지지 않도록 하단 배치를 검토하되 발표 화면에 빈 자막 바를 만들지 않는다. 정확한 크기와 안전영역은 실제 디스플레이에서 읽히는지로 결정한다.

내레이션에는 대명사만으로 화면을 가리키는 문장보다 대상을 밝힌 문장을 쓴다. 대사를 따라가는 자막은 마스터에 굽지 않고 별도 파일로 만든다. 실제 최종 음성과 동기화하고, 대본만으로 추정한 타임코드를 검증된 값으로 전달하지 않는다. 화면의 큰 글자는 대본 전문이 아니라 기억할 개념과 관계를 맡는다.

## 배포용 선택형 자막

검수한 SRT 또는 VTT를 제작 원본과 함께 보관하고 YouTube Studio의 별도 자막 트랙으로 제공하는 방식을 권장한다. 시청자는 CC를 켜거나 끌 수 있고, 오탈자 수정·번역 자막 추가를 위해 영상을 다시 렌더할 필요가 없다. 자동 생성 결과는 초안으로 취급하고 고유명사·수치·줄바꿈·타이밍을 확인한다. 필요하면 챕터별 읽기용 원고·핵심 요약도 함께 배포한다. 타 플랫폼에서는 해당 플레이어의 외부 자막 지원을 확인한다.

발표 시 CC를 끄고 시작·탐색·Break·재개·전체화면 상태에서 자막이 없는지 실제로 확인한다. YouTube 임베드의 `cc_load_policy=1`은 표시를 강제하지만, 이를 생략하거나 0으로 두는 것을 강제 숨김 보장으로 설명하지 않는다. 사용자 선호 설정이 적용될 수 있다. 현재 video-slide에 별도 자막 관리 기능이 있다고 가정하지 않는다.

공식 확인 기준(2026-09-17): [자막 추가](https://support.google.com/youtube/answer/2734796?hl=en), [CC 켜기·끄기](https://support.google.com/youtube/answer/100078?hl=en), [임베드 CC 파라미터](https://developers.google.com/youtube/player_parameters#cc_load_policy).

## 음향과 움직임

음성은 설명을 주도하고 BGM은 선택적으로 사용한다. BGM이 있으면 음성 구간에서 낮추고, 전환음을 모든 등장에 기계적으로 넣지 않는다. Break 전에는 말과 강조음의 잔향이 끝나게 하고 BGM도 자연스럽게 낮춰 정지/재개가 튀지 않게 한다. 마스터 전체의 대화 명료도·피크·크게 달라지는 음량을 확인한다. 특정 LUFS 값 하나를 모든 배포처의 보장값처럼 강제하지 않는다.

시각화의 움직임은 `등장 → 설명 중 변화 → 완성 상태`로 구성한다. 실제 효과의 길이는 음성과 읽기 속도에 맞춘다. 정적 화면에도 의미가 성립하도록 설계하면 발표 정지 화면의 품질이 좋아진다.

## 자료와 제작 방식

도식·차트·타이포는 SVG/HTML/React 등 편집 가능한 형태로 만들면 수치·문구 교체가 쉽다. 인물·배경·B-roll은 사용 권한과 출처를 프로젝트의 자산 목록에 남긴다. 출처 페이지, 사용 범위, 실제 자료/설명용 생성물 여부를 기록한다. 비공개 회의·지원자·고객 자료는 공개 스킬의 예제에 넣지 않는다.

기존 렌더 프로젝트가 있으면 재사용한다. 새 프로젝트에서는 대표 장면 하나로 무자막 레이아웃·동작·음성 및 별도 CC 표시를 확인한 다음 확장한다. Remotion을 고르면 결정적인 프레임 계산, HyperFrames를 고르면 재탐색 가능한 시간 제어와 해당 도구의 계약을 따른다. 이 스킬은 렌더 엔진이나 유료 생성 도구를 번들하지 않는다.

작업물 예시:

```text
project/
  brief.md
  script.md
  plan.json
  sources.md
  media/
  composition/
  renders/master.mp4
  captions/ko.srt
  handoff-v1/
    public-breaks.json
    manual-breaks.md
    presenter-notes.private.md
  review.md
```

## 검증 순서

1. 내용을 검토한다. 배포 시청자가 꼭 알아야 할 정보를 발표자 메모에만 넣지 않았는지 확인한다.
2. 대표 장면을 렌더하고 읽기·강조·출처·음성을 확인한다. 정지 프레임뿐 아니라 동작 중간도 본다.
3. 전체 영상을 연속 시청해 맥락과 음성 연결을 확인한다. 전환·속도·불필요한 반복을 수정한다.
4. 각 Break의 직전·정지·직후 프레임과 오디오를 확인한다. `at ± 0.6초` 안에 화면 전환이나 음성이 들어오는지 검토한다.
5. 최종 마스터의 실제 길이와 fps를 미디어 도구로 확인한다. 계획과 다르면 편집 원본/계획을 먼저 맞춘 뒤 입력표를 다시 생성한다.
6. YouTube에 업로드한 경우 최종 영상 ID·길이·재생 가능 여부를 확인하고 video-slide에서 Break를 입력·리허설한다. 정지 시 YouTube의 UI가 나타나는 상태까지 고려해 읽기와 메모를 확인한다.

`plan.mjs`가 검증하는 것은 선언된 타이밍과 데이터 구조이다. 실제 픽셀, 의미, 음향, 권한, 재생 안정성은 별도 확인이 필요하다. 검증 기록에는 계획 검증, 렌더 검증, 연속 시청, 서비스 리허설, 게시 완료를 각각 실제 수행 여부대로 기록한다.

YouTube 업로드 전에는 MP4와 Break 자료로 인계할 수 있다. 서비스에 입력하거나 게시하지 못했다면 남은 단계와 이유를 구체적으로 적는다. 발표용 PDF·슬라이드·무음 버전은 필요할 때 추가하며 기본 작업을 불필요하게 늘리지 않는다.
